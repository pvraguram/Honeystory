Implementation 01
Live Web Upload & Multi-Subsystem Ingestion Pipeline
How log files are uploaded dynamically by the user through the web interface, validated, mapped to aircraft racks, and ingested into analytical storage on the fly.
1 The Actual Workflow When Working
Step 1
User Upload via Web UI (ingest-modal.tsx)
The data logs are not pre-stored on the machine. The user opens the web application, clicks "Ingest Aircraft Logs", and drags & drops one or more HTML log files (.html / .htm). The UI automatically previews the detected computer channel (Node A, Node B, Node C) and log family (State, Fault, CI_BPQ, LBPQ, Transition) before submission.
↓
Step 2
FastAPI Multipart Ingestion Endpoint (server.py)
The web browser sends a POST request with the files to http://localhost:8000/api/upload-and-ingest?flight_id=AA100. FastAPI streams and writes the uploaded files into the active processing directory for that flight.
↓
Step 3
Pre-Database Structural Reconnaissance (recon.py)
Before touching the database, an inspection pass analyzes table structures. It samples 50 cell values per column and tests regex patterns. If real timestamps are confirmed with at least 50% confidence, the table is approved. Tables without timestamps are recorded in an audit manifest so nothing is silently lost.
↓
Step 4
Explicit Subsystem Hardware Mapping (node_mapping.py)
Resolves each file against node_mapping.json to decouple physical filenames from aircraft hardware racks: NODE_A maps to Left Rack (Master Channel), NODE_B maps to Right Rack (Standby Channel), and NODE_C maps to Auxiliary Rack (Spare).
↓
Step 5
Schema-Agnostic EAV Extraction (extractor.py)
Extracts rows into an IngestionRecord model. Rather than enforcing a fixed column schema that crashes when firmware formats change, it stores universal coordinates (node_id, table_id, row number, timestamp) plus a dynamic payload dictionary (fields: dict[str, Any]) holding whatever key-value attributes are present.
↓
Step 6
Clock Normalization & Analytical Storage (timestamps.py & storage.py)
Standardizes multi-format timestamps into continuous floating-point seconds from midnight (τ), checks for midnight rollover and asynchronous clock jitter, and writes the batch into DuckDB and partitioned Parquet files.

3 The Actual Methodology in Plain English

The Problem: In real flight testing, log files do not sit pre-loaded on the server. Different engineers upload logs through a web browser whenever an aircraft lands. Furthermore, the logs from the 3 flight computers (Node A, Node B, Node C) are completely inconsistent: some are wide tables, some are bullet lists, and some are raw key-value dumps. Hardcoding column names caused previous systems to crash on upload.

How we solved it: The user simply drops the files into the web browser modal. The browser uploads them to a Python FastAPI backend. The backend inspects the files before touching the database: it tests 50 actual cell values with regex formulas to confirm whether real timestamps exist, strictly maps each file to its physical aircraft computer rack via a configuration file, and stores each row as universal coordinates plus a dynamic dictionary. This ensures that no matter what columns or formats are in the uploaded files, the ingestion never crashes and zero rows are lost.

Implementation 02
Domain Translator & Context Synthesis Engine (translator.py)
Transforms cryptic binary registers, BITE codes, memory addresses, and pilot keypad indices into human-readable flight deck actions and safety advisories.
1 The Actual Workflow When Working
Step 1
Ingest Machine Data Fields
Receives raw extracted log rows containing cryptic hardware parameters: BITE 6025, Memory 402656480, Button 4869, ARINC Command 4294967172, Dual Mode 1, Opposite OK 0.
↓
Step 2
Layer 1: Domain Mapping Dictionaries (translate_field)
Decodes raw numbers against aerospace specifications: button 4869 translates to "INIT (Initialization) Key", memory 402656480 converts to Hex 0x18000CE0 (CPU Instruction Trap / Stack Boundary Violation), and command 4294967172 decodes to ARINC-429 standby channel invalidation.
↓
Step 3
Layer 2: Contextual Subsystem Synthesis (synthesize_event_headline)
Inspects the event family. For faults, it identifies the failure mechanism, the Deos RTOS daemon PID, and the recovery action. For state changes, it checks cross-talk status. For pilot inputs, it determines who acted (Captain vs First Officer) and their navigation goal.
↓
Step 4
Domain Classification & UI Export (classify_event)
Classifies each translated record into one of 4 clean domains: SYSTEM_ERROR (critical alerts), PILOT_INPUT (cockpit MCDU actions), NAVIGATION (flight guidance), or TELEMETRY (routine heartbeat).

3 The Actual Methodology in Plain English

The Problem: When an aircraft experiences a glitch, the raw logs output numbers like "BITE 6025" or memory addresses like "402656480". To human evaluators, pilots, or airline safety inspectors, these numbers mean nothing and give no explanation for why redundancy was lost.

How we solved it: We built a domain translator with two layers. The first layer converts numbers into aerospace terms (such as turning 402656480 into hex 0x18000CE0 to identify a CPU instruction stack trap). The second layer looks at the context of the whole event: it identifies who did the action (Captain or First Officer), what RTOS daemon failed (PID 653), and what safety recovery occurred (automatic FMS service restart). This turns cryptic dumps into clear sentences like: "BITE Fault 6025: Process Identity Lookup Failure (PID 653) — Automatic Recovery: FMS Service Restart."

Implementation 03
Log Correlation & Root Cause Causal Graph (LogCorrelationLayer)
Clusters event floods within a 15-second sliding window, builds a Directed Acyclic Graph (DAG), and calculates the downstream blast radius of faults.
1 The Actual Workflow When Working
Step 1
Event Normalization & PID Parsing
Normalizes incoming diagnostic lines and extracts Deos process identifiers (such as PID 653) from raw fault descriptions.
↓
Step 2
Sliding Window Clustering & Flood Debouncing
Clusters events that occur within 15 seconds of each other. Debounces duplicate error floods by counting occurrences and saving source log line IDs as evidence.
↓
Step 3
Causal DAG Construction (NetworkX DiGraph)
Applies known causal propagation rules to connect nodes: BITE 6074 (file EOF) → BITE 6025 (PID fail) / 6035 (bind fail) → BITE 6029 (mutex timeout) → BITE 6000 (deadline missed) → 11631-11633 (receiver timeouts).
↓
Step 4
Root Cause Scoring & Blast Radius Calculation
Identifies all nodes with zero incoming edges (true root causes) and calculates their downstream blast radius (the total number of impacted subsystems).

3 The Actual Methodology in Plain English

The Problem: When a software component fails in an avionics computer, it triggers dozens of secondary alarms all at once. An evaluator sees 50 errors pop up at the same timestamp and cannot tell which single failure started the chain reaction.

How we solved it: We group errors that happen within 15 seconds into a single cluster. Then, using a cause-and-effect graph (DAG), we link each failure to what it caused: for example, a file read error (Fault 6074) caused a process ID lookup to fail (Fault 6025), which locked an OS mutex (Fault 6029), which caused a background task to miss its scheduling deadline (Fault 6000). The algorithm scores each root cause by counting how many downstream systems it broke (its blast radius), identifying the real origin of the problem immediately.

Implementation 04
Flight Story & Mission Trajectory Reconstruction (dataset_builder.py, timestamps.py)
Synthesizes thousands of uploaded log entries into a continuous chronological flight story with automatic flight phase tracking and incident timeline markers.
1 The Actual Workflow When Working
Step 1
Master Timeline Merging
Consolidates extracted rows from the uploaded Node A, Node B, and Node C files into a unified master array and sorts them strictly by normalized epoch seconds.
↓
Step 2
Delta Time (Δt) Relative Offsets
Calculates the relative time difference (Δt) between consecutive packets to provide human-readable relative time markers (+0.25s, +2m 14s) from mission start (T0).
↓
Step 3
Dynamic Flight Phase State Machine
Tracks altitude transitions and climb flags to dynamically determine current flight phase: Pre-Flight Gate Setup → Climb Ascent → En-Route Cruise → Step-Down Descent → ILS Approach & Landing.
↓
Step 4
Incident Milestone Tagging
Pins significant events (faults, crew inputs, and redundancy drops) directly to their corresponding altitude and phase coordinates along the flight trajectory.

3 The Actual Methodology in Plain English

The Problem: When log files are uploaded, they contain thousands of separate events recorded at different rates by different computers. Without stitching them together, you have a pile of disconnected rows rather than a clear story of what happened during the flight.

How we solved it: We merge all events into one single timeline ordered by time. We track the airplane's altitude from ground level at the gate, climbing to 18,000 feet, and descending back for landing. By tying each diagnostic event to the airplane's flight phase and altitude, evaluators can clearly see: what happened at the gate (initialization fault), what happened during climb (pilot entered cruise flight level), and what happened at cruise altitude (partner FMS lost heartbeat and switched to single mode).

Implementation 05
Live Web Visualizer & Avionics Redundancy Dashboard
The interactive web platform where users upload logs, filter events by computer channel or severity, and inspect live cockpit telemetry and redundancy status.
1 The Actual Workflow When Working
Step 1
Initial Load (No Pre-Loaded Logs)
The user opens the web application (Next.js on port 3000 or the standalone HTML dashboard). The interface initializes with an empty state or status overview, ready to receive aircraft logs.
↓
Step 2
Interactive Log Upload & Live Status Query
The user opens the Ingestion Modal, selects their aircraft files, and uploads them to the FastAPI backend. Upon completion, the UI queries GET /api/status to update total records and node counts.
↓
Step 3
Dynamic Filtering & Flight Scrubbing
Users can filter the timeline by Node (Node A, Node B, Node C), Domain (System Errors, Pilot Inputs, Navigation, Telemetry), or search keywords. Evaluators can scrub through the flight trajectory slider to observe altitude and incident changes.
↓
Step 4
Flight Data Reset / Deletion (delete-aircraft-modal.tsx)
Users can click "Delete Aircraft Logs" to call POST /api/delete-flight?flight_id=AA100, which purges the DuckDB database, clears Parquet files, and resets the interface back to zero records.

3 The Actual Methodology in Plain English

The Problem: Aviation evaluators need a fast, responsive interface where they can upload new flight logs, immediately review decoded events, filter by channel, and cleanly delete data when testing a new flight scenario.

How we solved it: We built a clean web visualizer. It starts empty or queries the backend for the current status. The user uploads logs directly through the web modal, the system ingests and translates them on the fly, and the dashboard immediately updates with live record counts, filtered views, and cockpit gauges. When finished, the user can reset the system with a single click, completely deleting the flight's records from disk and database so the system is ready for the next test run.
